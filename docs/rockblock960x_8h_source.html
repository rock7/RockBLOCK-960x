481/* --------------------------------------------------------------------------
482 * SBD sessions
483 *
484 * These follow the SBD protocol one step at a time, and the driver never
485 * starts a session by itself: every AT+SBDIX (which can cost credits) comes
486 * from a call to rb960xInitiateSession() or rb960xInitiateSessionAsync().
487 * Retrying is up to the application; the result's moResult says why a
488 * session failed. A typical send:
489 *
490 * 1. rb960xSessionReady() - cheap local checks and the last signal.
491 * 2. rb960xWriteMoBuffer() - load the message (local, free).
492 * 3. rb960xInitiateSession() - run the session (sends the MO message and
493 * checks the gateway for MT messages).
494 * 4. If the result's mtStatus is 1, rb960xReadMtBuffer().
495 *
496 * To check for MT messages without sending anything, clear the MO buffer
497 * with rb960xClearBuffers() and initiate a session: the MO buffer is not
498 * emptied by a successful session, so otherwise it would be sent again.
499 * ------------------------------------------------------------------------ */

802/* ==========================================================================
803 * Low-level AT commands
804 *
805 * Each function sends one AT command and returns the modem's reply as-is,
806 * without parsing it or updating the context. Prefer the high-level API
807 * above; these are for features it doesn't cover yet.
808 *
809 * Common to all of them:
810 * - @p rb must be an initialised context. It is not checked for NULL.
811 * - Where there is a @p resp buffer, it receives the information line(s)
812 * from the reply, without the final "OK".
813 * - They return RB960X_OK, RB960X_ERR_TIMEOUT if the modem didn't respond
814 * in time, or RB960X_ERR_PROTOCOL if it replied with something other
815 * than "OK".
816 * ========================================================================== */
